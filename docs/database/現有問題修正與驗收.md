# 現有問題修正與驗收（2026-11-02，台灣時間）

> 2026-11-06狀態註記：下文保留該批歷史規格／驗收事實，不能當作現行產品基準或最新全量測試。最新依行政資料01／02與 [目前進度](../../行政資料/進度與待辦/進度執行表.md)；套房合併、免面積來源、舊C01及無限公開等過往決策若與新版R02／02-01／02-09衝突，均已被取代。新欄位、完整上架與正式容量尚未全部接妥。

本批只修現有驗證與儲存不一致，不新增登入、草稿 API 或上架服務，不改兩份企劃原文。

## 已修正

1. 押金月數接受任意正數，但資料庫為 DECIMAL(12,4)：輸入可能被捨入、溢位或捨入為零後遭 CHECK 拒絕。現於驗證層拒絕無法原值保存的數值，保留小數月數，不自動四捨五入。這是目前資料欄位容量，不是新訂押金政策或商業上限。
2. 坪數具有相同 DECIMAL(12,4) 問題，改用相同精度檢查，保留 Prisma Decimal 的精度，不先轉 number 判斷小數位。
3. 金額、格局數、陽台數與樓層等輸入原接受超出 PostgreSQL INTEGER 的值；現依既有欄位容量驗證，不讓驗證成功的數值直接因整數溢位失敗。沒有新增合理租金或合理樓高門檻。
4. 陽台「無」與共用空間「陽台」不能同時成立；回傳共用空間欄位錯誤。不把「專用陽台＋另有共用陽台」視為矛盾。
5. 規格對照文件更新已確認選項與已完成儲存欄位／mapping 的狀態，保留未串接 API／權限／完整發布檢查的限制。

## 驗證證據

- 先新增回歸案例，在修正前重現 7 個失敗案例；修正後通過。
- 獨立 PostgreSQL 暫存 cluster 驗證 0.0001、1.2345、99999999.9999 押金月數，以及坪數邊界原值往返，INTEGER 最大值可存取。
- 不可表示精度的押金輸入在產生更新資料前失敗；既有草稿列不變。
- 型別檢查、編譯、整體測試及 git diff --check 通過；測試數量以本次執行結果為準。
- 未執行現有開發庫／正式庫遷移，沒有修改 Prisma schema 或既有 migration。本批的資料庫寫入僅限測試建立的暫存 cluster，結束清除。
- 已有 Prisma/pg 並行 query 棄用提示仍出現；未擅自升級依賴。

## 待決／本批不處理

- 樓層：使用者後續已確認「一般正整數樓層不得高於總樓層」，單層與範圍兩端皆已檢查並回傳對應欄位問題，支援地下樓及等於總樓層的邊界。0 樓、夾層、屋頂加蓋等特殊表示方式仍待決；本次不新增或宣稱支援特殊樓層規格，也不清洗舊資料。
- 陽台模式是否只能有單一使用方式、共用清單與陽台選項未來如何在 UI 合併呈現，不能由後端自行重新定義。本批僅拒絕明確自相矛盾的「無＋有共用」。
- Property.floor 與 Listing.floorFrom/floorTo 的核對、地址待確認公開版本與分組流程仍未建立。不將其視為已修完的公開地址功能。
- 兩個局部檢查器尚未由完整上架服務整合；權限、額度交易、圖片實際處理仍缺，檢查成功不得直接授權上架。
- 分區儲存目前是完整替換，不是允許缺項的草稿 PATCH。不得將未填欄位直接套用為清空使用者舊資料。
- 金額整數新台幣沿用既有專案；未決精度或稅務政策不在本批定案。
