# 11 部署、發布與恢復

版本：2026-11-07規劃基準。這是正式／預備環境的操作設計，不是ChatGPT開發環境的「儲存並發布」說明；GitHub push、環境快照、網站部署及DB migration是四件不同的事。本輪沒有執行任何部署、備份、還原或正式遷移。

## 11-01 部署前必要資料

正式與預備主機／region／負責帳號、網站／API／圖片網域、TLS／DNS、DB與備份、worker執行方式、秘密管理、外部回呼與outbound、供應商資源及費用責任要有清單。帳號與資源歸負責人或公司，不讓個人開發帳號成唯一控制者。

主機須能跑Node API、持久worker及圖片處理原生依賴；不把R2當運算主機，不假設僅部署前端就有後端／資料庫。具體供應商與預算仍見總覽D01，未定不能宣稱可用正式網址。

正式選型硬條件：API、必要背景程序及資料庫不因閒置休眠；開發Hobby可用，正式不得直接沿用未滿足此條件的配置。工作區商用方案與個別付費實例分開核價／驗證；Pro工作區不等於已買常駐運算。放行須有閒置／無流量排程、負載與擴容監控、重啟及備份還原證據，未過不標正式可用。

## 11-02 發布物與流程

1. 以確定commit及lockfile建立不可變artifact，保存Node／Prisma／OS／原生套件與建置摘要；禁止正式主機直接拉latest邊裝邊改。前端與API／worker的契約版本可追蹤。
2. CI／人工檢查同一流程：靜態型別、依賴／秘密掃描、隔離整合測試、build、migration從空庫與去識別副本、公開DTO／安全負向及必要UI／外部驗收。未有CI時不能假稱GitHub有自動把關。
3. 同一artifact先到預備環境，套相容遷移、設定及回呼，執行10的關鍵煙霧與故障案例；預備只能向測試帳號寄信／sandbox付款，不連真商戶當測試。
4. 正式放行核對功能就緒、未解阻擋、備份與可還原證據、回退版本、變更影響、通知與值班；記明放行人。需要真實費用／資料操作依已授權範圍，不因寫完企劃視為授權啟用外部付費。
5. 先套expand相容資料變更，啟動新API／worker、readiness通過後導流；功能旗標與遷移分開，worker不可同時重做同一操作。保留上一個可相容artifact與設定。
6. 正式煙霧只用受控帳號及最小必要流程，檢查公開隱私、登入／草稿、任務、webhook、取消入口及通知，不建立假付款／查核；監看錯誤、DB與積壓後宣告結果。
7. 失敗可停止導流／功能並回前相容artifact；資料結構回復是另一決策，不能自動向下遷移刪欄或還原整庫吞掉新交易。記錄開始／結束、結果與未完成補處理。

## 11-03 資料庫遷移

- 沿04的expand／回填／切換／contract；已套過的migration不改歷史。正式禁止reset／drop／以seed重設營運地區或假造資格。
- 每批列鎖表／時間、資料規模、索引建立及舊新應用相容性；備份後演練相同SQL和驗證query。長操作有停止／恢復方式，不和應用自動啟動綁一起。
- 驗證筆數、FK／唯一、角色、價格來源、資格起訖、退款餘額、公開／草稿／封存與容量、資產引用與首刊。差異不明即停，不以刪舊資料「修好」。
- 回退策略要列新資料是否可被舊程式解讀；不可者先關該功能而非盲退。已確認支付／公開版本／刪除不可因回退消失或重新生效。

## 11-04 備份設計與恢復目標

| 類別 | 規劃要求 |
| --- | --- |
| PostgreSQL | 自動一致性備份、支援時PITR、加密與隔離權限；監測成功、可下載及實際可還原 |
| R2資產 | 正式資產manifest、版本／權屬／大小／清理記錄與可用副本策略；不能因R2可靠就說不需備份 |
| 秘密／設定 | 保存安全版本與復原權限，秘密另保護，不把明文塞DB dump或Git |
| 供應商事實 | 訂單／事件參照及查詢／對帳能力，還原後重新核對付款、退款、取消與續扣 |
| 刪除／撤銷 | 保留必要防復活標記、已永久刪除／隱私撤銷／取消授權事實的恢復程序，不重放舊事件變新 |

RPO（可接受資料損失時間）、RTO（恢復時間）需負責人核對成本與營運需求。工程候選目標可先以DB RPO≤1小時、RTO≤4小時討論，**未核定／未演練不算承諾**，也不表示R2／金流能同時點還原。備份保留期、異地副本與費用見12及D03，不能空白就上線。

## 11-05 事故恢復步驟

1. 判斷事故範圍，必要時停止新付款／退款／發布／交接／清理，不隨意停掉取消／客服權利入口；保存時間線與最小證據。
2. 選可驗備份與隔離環境還原，不先覆蓋正式；記資料截至點、遺失窗口與檔案manifest一致性。缺檔標不可用不直接公開破圖或私有內容。
3. 重套永久刪除、隱私撤銷、管理權變更及帳戶限制等必要事實；對過期session作安全失效處理，不復活已取消續扣或已結案退款。
4. 對供應商重新核對恢復點後付款／退款／取消等結果，以原唯一操作參照對帳；不直接重播所有Outbox扣款或退款，外部無冪等查詢能力則人工核對。
5. 重建可重建的公開索引／快取／計數，先私有核對再開公開；worker按安全lease及版本續跑，清理不得刪掉仍被新恢復內容合法引用的資產，也不能復活永久刪除內容。
6. 通過最小10驗收、記實際RPO／RTO及資料差異，授權責任人分階段恢復。向受影響者說已知事實與後續，不宣稱所有資料完全無損。

## 11-06 隱私與帳務緊急處理

隱藏地址洩漏先停不安全公開版本與平台可控圖片／卡片出口，再處理cache與證據；不能為維持可用繼續洩漏。疑似重複扣款先停相關新交易、查原意圖及供應商事實，保留取消／退款案件，不立即全庫回復以免更多雙重返還。

秘密洩漏撤銷／輪替、限制存取與稽核，不能只刪日誌或commit。公告、個資通知與時限依法／正式條款由E05／12處理，不由工程文件猜法律要求。

## 11-07 完成證據

至少一次：從備份在隔離環境實際還原、外部對帳、刪除／取消不復活、artifact回退、新舊migration相容及worker重啟演練。報告列耗時、遺失窗口與未解；只有「有dump檔」不算能恢復。本章規則完成，不表示上述操作已執行。
